# 2. Phase 1 — LOGIC

## 2.1 Define the Expense Resource

An expense represents a financial transaction.

Example:

```json
{
  "id": 1,
  "name": "Groceries",
  "amount": "85.50",
  "category": "Food",
  "date": "2026-11-23"
}
```

### Expense Fields

| Field | Data Type | Required | Description |
|---|---|---|---|
| id | Integer | Server-generated | Unique expense identifier |
| name | String | Yes | Expense description |
| amount | Decimal | Yes | Expense amount |
| category | String | Yes | Expense category |
| date | Date | Yes | Expense date |

### Validation Rules

- `name` must not be empty.
- `amount` must be greater than zero.
- `category` must not be empty.
- `date` must be a valid date.
- `id` is generated by the server.
- Clients do not provide an ID when creating an expense.

CRUD represents four fundamental resource operations.

| Operation | HTTP Method | Endpoint | Purpose |
|---|---|---|---|
| Create | POST | `/expenses/` | Create an expense |

## 3.3 Pydantic Models

### Request Model

```python
class ExpenseCreate(BaseModel):
    name: str = Field(min_length=1)
    amount: Decimal = Field(gt=0)
    category: str = Field(min_length=1)
    date: date
```

**Purpose:** Validate incoming expense data.

### Response Model

```python
class ExpenseResponse(ExpenseCreate):
    id: int
```

**Purpose:** Define and validate the expense data returned by the API.

### Why Use Separate Models?

`ExpenseCreate` does not include an ID because the client should not generate one.

`ExpenseResponse` includes the ID because the server generates it and returns it to the client.

---

## 3.4 In-Memory Storage

```python
expenses: list[ExpenseResponse] = []

next_expense_id = 1
```

### Responsibilities

- `expenses` stores expense objects.
- `next_expense_id` tracks the next available ID.
- IDs increase as expenses are created.
- Deleting an expense does not reuse its ID.

### Limitations

Data is lost when the application process restarts.

This implementation is not designed for multiple worker processes or concurrent writes.

## 3.5 Endpoint Implementation Framework

Use the following framework when implementing every endpoint:

### Step 1 — Define the Endpoint Contract

Identify:

- HTTP method.
- Resource URL.
- Request parameters.
- Request model.
- Response model.
- Expected status codes.

### Step 2 — Implement the Route Decorator

Define how FastAPI maps an HTTP request to a handler.

Example:

```python
@app.post(
    "/expenses/",
    response_model=ExpenseResponse,
    status_code=201
)
```

### Step 3 — Identify Decorator Components

| Component | Purpose |
|---|---|
| `@app.post` | Registers a POST route |
| `"/expenses/"` | Resource URL |
| `response_model` | Defines the response schema |
| `status_code` | Defines the success status |

### Step 4 — Define Handler Logic

Write the processing steps before implementing the function.

### Step 5 — Implement the Handler

Example:

```python
def create_expense(expense: ExpenseCreate):
    global next_expense_id

    new_expense = ExpenseResponse(
        id=next_expense_id,
        **expense.model_dump()
    )

    next_expense_id += 1

    expenses.append(new_expense)

    return new_expense
```

### Step 6 — Identify Handler Components

| Component | Purpose |
|---|---|
| `def create_expense` | Defines the handler |
| `expense: ExpenseCreate` | Receives validated request data |
| `global next_expense_id` | Allows updating the module-level counter |
| `ExpenseResponse(...)` | Creates an expense object |
| `model_dump()` | Converts the Pydantic model into a dictionary |
| `expenses.append()` | Stores the expense |
| `return` | Returns the created expense |

### Step 7 — Test the Endpoint

Verify successful behavior and expected errors.

## 3.9 PUT `/expenses/{expense_id}` — Update Expense

### Route Decorator

```python
@app.put(
    "/expenses/{expense_id}",
    response_model=ExpenseResponse,
    status_code=200
)
```

### Handler Function

```python
def update_expense(
    expense_id: int,
    updated_data: ExpenseCreate
):

    for index, expense in enumerate(expenses):

        if expense.id == expense_id:

            updated_expense = ExpenseResponse(
                id=expense_id,
                **updated_data.model_dump()
            )

            expenses[index] = updated_expense

            return updated_expense

    raise HTTPException(
        status_code=404,
        detail="Expense not found"
    )
```

### Processing Logic

1. Receive expense ID.
2. Receive replacement expense data.
3. Validate request data.
4. Find the existing expense.
5. Create the replacement object.
6. Preserve the original ID.
7. Replace the stored expense.
8. Return the updated expense.

**Expected Status:** `200 OK` or `404 Not Found`

### 4.3.4 Test Isolation

Because Feature 01 uses global in-memory storage, tests must reset application state.

Without isolation, one test could affect another.

Use a pytest fixture:

```python
@pytest.fixture(autouse=True)
def reset_expenses():

    # Setup
    main.expenses.clear()
    main.next_expense_id = 1

    yield

    # Cleanup
    main.expenses.clear()
    main.next_expense_id = 1
```

### Fixture Components

| Component | Purpose |
|---|---|
| `@pytest.fixture` | Registers fixture |
| `autouse=True` | Applies fixture automatically |
| `main.expenses.clear()` | Clears expenses |
| `main.next_expense_id = 1` | Resets ID counter |
| `yield` | Separates setup and cleanup |

# 8. Known Limitations

Feature 01 intentionally uses in-memory storage.

Current limitations:

1. Expenses disappear when the application restarts.
2. Data is not shared between multiple application processes.
3. Concurrent modifications are not protected by database transactions.
4. No authentication or authorization exists.
5. Expenses are not associated with users.
6. No filtering, sorting, or pagination exists.
7. No persistent database is configured.

These limitations will be addressed in future features.
